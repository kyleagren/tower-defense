# Hub & Dev Tools

A deliberately bare-bones staging area — meshes and colored boxes, no art pass — of two rooms connected by a hallway (`res://levels/hub/hub.tscn`, the first level `LevelLoader` loads).

- **Room A — selection and stations.** `CharacterSelectStation` lists Soldier/Tank and swaps the player's live body on pick. `LevelSelectStation` lists playable levels and loads one through `LevelLoader`; only the host can use it. The crafting table and vendor ([items.md](items.md)) sit in the remaining corners, and the **stash** chest against the west wall between the vendor and level select. All stations share one `StationInteractor`: a station just implements `IInteractable` (`GetPromptText`/`Interact`), so a new station type never needs new interactor wiring.
- **Room B — DPS testing.** The hub follows Build's rules everywhere, so Rituals go down through the ordinary build menu against free mana, with the Sentinel's own weapon and abilities working alongside them. Tokens can be authored here but not deployed. Training dummies are placed in groups of **1 / 4 / 8** across three corners, to separate single-target from multi-target and AoE testing.
- **Unlimited economy, hub-only.** `EconomyManager.Unlimited` short-circuits every mana and capacity check. `WallPlacementFlow`'s segment-affordability check reads the same flag directly, since otherwise an Ice Wall's _drag length_ stayed capped even though placing it was free. Chosen over a huge starting pool so mana stays a concept that only exists inside a real match.
- **Dev keys** (`DebugToggle`): F1/F2 raise/lower the Tank's heat by 20; F3 fills the Soldier's Harvest gauge from one random element, ready for Overdrive. Wired into the hub as well as real levels, since the hub is where they're most useful.
- **Display toggles** (`DebugSettings`): enemy health bars, weapon damage numbers, Ritual damage numbers, which shoulder the camera sits over (applied live, to the player's own camera only) and screen shake, switched from the pause menu's Options screen. Saved per machine to `user://settings.cfg` with Godot's `ConfigFile`, not in the player save — they're this machine's preferences, not part of anyone's progress. Hiding health bars also updates enemies already alive, since each otherwise reads the flag only on spawn.
- **Video options** (`VideoSettings`, same Options screen, own file `user://video.cfg`): resolution, glow, ambient occlusion and shadows. Godot's fullscreen never changes the monitor's mode, so a lower resolution renders the 3D world smaller and upscales it with FSR while the UI stays sharp. The level's environment and sun are its own nodes, so `LevelContext` applies these on every level load as well as on a change. Tonemapping is left out — it costs next to nothing.
- **Shader warm-up** (`ShaderWarmup`). The first level loaded in a run — normally the hub — spends the back 60% of its loading bar ("Preparing effects") drawing every effect's meshes, particles and materials in front of the camera a few at a time, so their shaders compile behind the loading screen rather than as a hitch the first time an effect shows up mid-wave. Bare copies are drawn, never the scenes themselves, so no script runs. What to draw is a manifest (`core/shader_warmup_manifest.tres`) built by an editor plugin: **Project > Tools > Rebuild Shader Warm-up Manifest**, to re-run after adding effects. It skips levels (which compile their own materials as they load) and `ui/`, and warns about any listed file since moved or deleted.
- **Floating combat text** is capped at a fixed count via `ActiveRegistry`, oldest evicted first — a zero-cooldown tower with chain, fork and salvo stacked could otherwise keep hundreds alive and cost over 100fps.
- **Players collide with the `Obstacles` layer.** This is a real gameplay rule, not a hub detail: `IceWallSegment` sits on that layer alone, so before this the player could walk through their own wall despite the design always saying otherwise.

**Not built:** a real art pass, and any detail beyond a name in the selection panels — no thumbnails, stats or descriptions.

## Main menu and save profiles

- **Main menu (`MainMenu`):** Play / Settings / Exit — no Singleplayer/Multiplayer split, since multiplayer is just the hub with its lobby open ([architecture.md](architecture.md), Multiplayer). Settings is the existing Options screen. A plain dark backdrop for now; a lit 3D one is a later polish pass. The pause menu's **Main Menu** button leaves any session on the way — for a host, today that ends the session for everyone else; under host migration ([architecture.md](architecture.md), Multiplayer) the party would carry on without them.
- **The menu is a local overlay, not a level.** It lives in `main.tscn` beside `LevelLoader`, outside the `Level` node, so the level spawner never replicates it; it shows only while no level is loaded, and Play loads the hub.
- **Save profiles (`SaveManager`):** each profile is its own JSON file under `user://profiles/` ([architecture.md](architecture.md), Save format), with a name and last-played time stored inside it. Play goes straight in on the only profile, to a picker when there are several (name, gold, last played; New and Delete, confirmed with Cancel focused), and to naming a new one when there are none — prefilled "Profile N", so a controller can confirm without typing. **Up to 20 profiles**, a cap to revisit only if someone gives a reason. A save from before profiles becomes "Profile 1", its old file kept beside it as `save_data.tres.bak`. Settings (`settings.cfg`) stay shared across profiles, since they're the machine's preferences, not anyone's progress. A profile's name is only ever shown to its owner — in co-op, other players will see your Steam name. Steam Auto-Cloud can sync `user://profiles/` by configuration alone.
- **Starter weapons:** every profile gets one plain weapon (Common, no mods) per Sentinel, once — equipped if that Sentinel's weapon slot is empty, otherwise put in Inventory (and tried again next load if Inventory is full). Each profile records which Sentinels have had theirs, so a Sentinel added later gets one on the next load and vendoring it is never repeatable.
- **Protecting saves.** Steam Cloud syncs the latest file between machines but keeps no history, so it can't undo a bad save. Each write goes to a temporary file that then replaces the real one, so a crash mid-write leaves the last good save. Every successful load copies the file into that day's backup, overwriting any earlier one from the same day, and the newest 30 daily backups are kept — 30 days _played_, however far apart, so a bug that goes unnoticed for a few days doesn't take every copy with it. A profile that won't load shows in the picker as unplayable, with Restore (newest readable backup; the unreadable file is set aside, not replaced) and Delete; it's never silently replaced. Delete sends a profile and its backups to the recycle bin rather than erasing them. Backups from before the JSON format still restore.
- **Dev flags skip the menu.** `--host`, `--join [address]` and `--profile N` (`LaunchFlags`) boot straight into the hub. `--profile N` plays on profile N, creating it if needed; without it, the last-played profile. **Two instances on one PC need different `--profile` numbers**, or they share a save and the later write wins.
- **Joining needs a profile first**, since joining immediately sends the local profile's gear and Sentinel pick to everyone. Today that holds because an invite is only acted on in the hub, where a profile is always loaded. **Planned:** an invite accepted before one is picked — at the menu, or by launching the game from Steam — follows Play's own rule: straight in on the only profile, the picker first if there are several, naming one first if there are none. An invite accepted inside the picker joins once a profile is chosen.
- **Split-screen means one Steam account can hold several seats**, so a seat's stable identity ([architecture.md](architecture.md), host migration) is the Steam account plus the local player index, not the account alone.
