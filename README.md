# Runewarder — Design Reference

*(Working title — open to change.)*

Current state of the design, plus just enough "why" to avoid re-litigating settled decisions. Not a full history — see git log for that. Update this doc as decisions change; it's meant to stay short enough to actually read.

## 1. High Concept

3D, low-poly stylized tower defense combining:

* **Dungeon Defenders** — the player has direct combat presence, can't solo-carry the defense, and picks from a roster of fixed-kit characters.
* **Path of Exile** — towers cast a base skill ("Spell") plus stacked support "Runes." Composition over inheritance, deep build expression.

Single-player is built first. Invite-a-friend co-op is a hard requirement of the finished game, architected for from day one (simulation/rendering kept separate, data model kept serializable) rather than bolted on later.

**Theme (decided):** the Architect is a time-traveler. Years of hopping between eras and timelines, making friends and getting himself into trouble, has left cracks in reality behind him — and those fractures are letting monsters (and in some cases, imprisoned boss-tier figures whose bonds have weakened) run loose in the periods he's damaged. The campaign is him going back to each fracture to seal it. The fighting-character roster (Section 4) is drawn from people he's met and roped into helping along the way, rather than a single-era cast — this is *why* the roster can plausibly keep growing without needing a shared origin. Vertical slice stays confined to a single era/timeline — the multi-era version (distinct enemy rosters and visual biomes per period, not just a reskin) is the long-term vision, scope permitting. See Section 15 for what's still undecided.

**Engine:** Godot 4, C#. Chosen over Unity (trust concerns after Unity's 2023 pricing controversy) and UE5 (heavier engine, steeper learning curve for a lightweight stylized project). C# over GDScript for the simulation-heavy load (many enemies/projectiles/modifiers updating every frame).

## 2. Match Structure & Core Loop

* Fixed-path maps (not open-grid pathfinding), multiple lanes converging on one or more defendable objectives. Lane count is per-map, not a fixed game-wide number — same as most TDs.
* **Prep phase:** the Architect (mage, non-combat role) places towers within a fixed capacity budget and allocates runes. He also pre-crafts up to 3 "inscribed tokens" — fully-defined towers ready to deploy reactively — recraftable between waves.
* **Wave phase:** the player controls a fighting character with their own health. Tokens can be placed reactively mid-wave; towers otherwise can't be built or repositioned mid-wave (see Section 4 on repositioning). Enemies advance down lanes toward whichever defendable objective is closest and attack it continuously until it falls or the wave ends.
* **Objectives:** the primary one is the mage's own shell/force field — enemies attack it directly, and it falling ends the run. Harder maps add secondary objectives, **Energy Harvesters**, which siphon energy from slain enemies (mage-powered thematically, but function identically to the main shell, minus having a mage inside). This is how one mage "covers" more than one objective — the harvesters don't need his direct presence.
* Tower capacity is a fixed ceiling for the whole match — it doesn't grow over waves. Pacing comes from the economy (currency accrues over time), not capacity growth.
* Difficulty has two vectors: campaign progression (map-to-map, resolved via composition — richer enemy mixes, more objectives, more complex layouts) and difficulty *setting* (replaying a map at Easy/Medium/Hard, handled by enemy composition/timing — see Section 8 — not flat stat multipliers).
* Minimap shows monster positions, which lane/spawn point they're from, and disabled-tower status.

## 3. Player-Character & Meta-Progression

* The Architect gains persistent XP, tied to difficulty cleared (not matches played, to avoid grinding easy content into disproportionate power). XP unlocks an item slot of his own (Section 10's `Item` class — not thematically armor for a non-combat mage, but functionally the same system) — a passive, global buff applied to all towers. **One slot for now.**
* **Spell unlocks (decided):** new base Spells unlock as the Architect levels up on the same persistent XP track, rather than via per-map completion — keeps spell pacing tied to overall progression instead of needing its own separate per-map tracking system.
* These items drop with a randomized, tier-equal stat budget (e.g. Level 3: +30 to all stats plus a random ~90 bonus to one stat) — no item within a tier is objectively best, only best for a given build.
* Guardrail: this must never let the player's overall power outstrip the towers' — towers stay the dominant source of defensive strength regardless of meta-progression.
* Rewards scale with performance (objective health remaining, waves survived cleanly, time taken), not just clearing — exact magnitudes TBD.

## 4. Player & Characters

* The player deals direct damage and has their own health, but can't solo-carry the defense.
* Death: temporary respawn with a cooldown; an ally can revive faster, or the player can spend match-currency to skip the wait.
* Fixed-kit characters, not gem-built — keeps the "too much freedom → one optimal build" problem contained to towers.
* **Roster:** implementing **Soldier** first, to get a vertical slice working end to end. Tank, Assassin, Sniper, and Templar come later (Sniper/Assassin differentiation not yet designed — will exist, just undecided how; Templar's kit not designed either, but one skill idea already floated — something similar to PoE's Divine Ire, a channeled, ramping-damage release).
* **Character kit design principles (decided):** not every character needs the same four-slot template (e.g. CC + mobility + buff + panic button) — forcing that shape onto every kit risks each character being the same abilities reflavored. A character skipping CC or an emergency button isn't a gap that has to be filled per-character; the roster can compensate at a wider level (CC-granting tokens/items, an ally who has it). Four active abilities isn't a hard requirement either — the original goal was just "more to do than Dungeon Defenders' two," not a fixed count. A good kit mixes genuinely new mechanics this game's systems make possible (e.g. reading/manipulating an enemy's Status) with recognizable genre tropes reskinned to fit — not purely one or the other.
* **Reserved for other, undesigned characters** (so later kits don't collide with ideas already spoken for): **Detonate** — an elementalist-style character popping all elemental Statuses in an area for bonus damage; **Taunt** — drawing enemy aggro; **self-duplication/clone** — floated for Soldier, but shelved as fitting an illusionist/trickster-coded character better than a disciplined-soldier one.
* **Personal (per-ability) reactions — a second axis alongside Section 15's shared Reaction system:** an ability can check an enemy's current Status/Ailment and do something bespoke of its own if it matches, without that interaction needing a slot in the shared combination map (e.g. "if this hits a Water-Status'd enemy, do X instead"). The shared system is universal and symmetric (any tower/rune can trigger it); a personal reaction is scoped to one specific ability and doesn't have to follow the shared system's rules at all.
* **Soldier — kit draft (in progress).** Deliberately keeps one foot in "traditional shooter" appeal — not every character will have a gun/ADS, so Soldier is the one built to give that audience a reason to pick him — while still reading as part of this game's own systems rather than a bolted-on FPS minigame. Also leans on the roster's time-travel premise (Section 1): Soldier is implied to be from a future era, which is the in-fiction justification for the tech-flavored (not magical) pieces of his kit below.
  * **Passive, counts as one of the ability slots (not free):** a dual-mode Fire/Cold rifle (built-in elemental firing modes) plus the ability to socket a Rune into the rifle. Deliberately counted against the same power budget as everyone else's four slots, both because switching firing modes needs its own bind anyway and to avoid Soldier quietly having more total kit than a character without an equivalent passive.
  * **Ability — Health Link:** tether two enemies; damage one takes mirrors to the other (not a shared HP pool — a pair of beefy enemies standing together effectively doubles incoming damage on both). Implementation note for later: the mirrored damage instance itself must be flagged so it doesn't re-trigger the link on the other end, or it ping-pongs infinitely in one frame — same "don't cascade" pattern already used for Ailment ticks not re-marking Status.
  * **Ability — Weak-Point Visor:** while active, exposes a bonus-damage weak point on every enemy at once (chosen over a single-target-lock version for simplicity).
  * **Ability — Elemental-Sapping Nanites:** harvest Status/Ailments off enemies (exact trigger — passive drip vs. an active send-out button — not decided; may end up as a talent-tree choice rather than one fixed behavior) to fill a gauge; a full gauge unlocks a one-shot, lane-clearing raygun blast. Self-limits to a handful of uses per map by gauge-fill rate rather than a cooldown timer.
  * **Considered, not committed to a slot:** a rune-configured super-shot (an empowered next-shot whose effect depends on the socketed rune), reusing each Rune's own tunable numbers directly rather than routing the gunshot through `SpellCastContext`/the spell pipeline — would need a new, narrow `Rune` hook separate from `Apply(context)`, not a change to the shared spell-cast pipeline. Noted here so the idea isn't lost even though it isn't currently one of the four slots above.
* **Future-tech stretch goal, not committed:** a real Portal-style gun (enemies actually redirected through it, not just a player-only teleport) for some future character. The rendering problem is solvable in Godot (a `SubViewport` + second camera + oblique near-clip-plane trick is a known technique) — the real cost is that enemies path via `NavigationAgent3D`, which has no concept of falling through a portal and re-pathing from a landing spot. Touches rendering, physics, and enemy AI at once; worth an isolated prototype (just the render trick plus one dummy enemy re-pathing) before ever attempting it for real.
* The player can **repair** towers mid-match (funnel mana into a tower to restore it) but cannot **reposition** them once placed — the token system covers "I need a tower somewhere new, right now" instead.
* The Architect is a distinct, non-combat role — places/preps towers and pre-crafts tokens, then isn't part of the fighting roster (in-fiction: he's sustaining the shell).
* The player's own power system (health/damage/progression) is completely separate from the tower Rune system — not yet designed, but decided to share no mechanics with Runes.
* Character set bonuses: a planned but far-future itemization idea.

## 5. Tower & Rune System

* A base skill ("Spell," e.g. Fireball) is an immutable data definition (damage, speed, tags). Modifiers ("Runes") transform that definition and/or hook into its events. Composition, not subclassing.
* Tags (Projectile, AoE, Duration, Trigger, elemental types) let a Rune apply generically to "anything with tag X" instead of bespoke per-skill logic. Elemental tags exist for build-crafting depth, not enemy resistances — enemies have none, by design (Section 9).
* Elements confirmed so far: **Fire, Lightning, Cold, Wind.** More may be added later.
* Elemental reactions (Genshin "swirl"-style — bonus effect when a second element hits an already-elemented target) and trigger-chaining (PoE "Cast on X"-style — one skill's on-activate/on-break event fires a second skill) are both planned, reusing the same event-hook pattern.
* Runes are permanently available at low tier; higher tiers drop and are allocated across limited slots per tower. Towers don't level or scale in power within a match. Duplicate rune types on one Spell are disallowed (enforced in code).
* **Mana/capacity cost (implemented): PoE-support-style multiplicative, not per-rune-count.** Every `Rune` has a `ManaCostMultiplier` (base class default, applied automatically for every attached rune during resolve — no per-rune code needed unless a rune wants to deviate from the default) that multiplies onto the tower's resolved `ManaCost`, the same `base * (1 + increased%) * more` shape as Damage/Range/Capacity. Replaced the old flat "+X mana per socket filled regardless of what's in it" model. **Currently every rune uses a flat placeholder 1.2× (`Rune.ManaCostMultiplier`'s base-class default) for testing the mechanism end-to-end — not tuned per-rune yet, not a balance decision.** `MaxCapacity` is also a placeholder (1000) specifically to leave room to experiment with these multipliers before real numbers get chosen.
* Targeting: base skills have a natural default target priority (a Fireball leans toward ground targets); a dedicated targeting rune can override it. Player presence is never a targeting fallback — multiple lanes mean the player can only be in one place at a time.
* **Player interaction model (decided):** tower placement and aiming use a center-screen reticle + raycast into the world, not a screen-space mouse cursor. Keeps mouse and controller input unified under one system (no separate cursor-based UI to build for controller players) — full controller support is a requirement, not an afterthought.
* Some towers will eventually need line-of-sight raycasting — not implemented yet (currently pure distance checks, so a tower can shoot through walls).
* Player-buff towers (e.g. a "Buff Totem") buff the player instead of attacking — **range-based** (player must stand near it to benefit), costs capacity like any other tower.
* **Tower visual direction (decided):** If every tower is fundamentally magical, you don't necessarily need to change the tower's physical shape for every spell.
  Imagine the base tower is basically:
  a floating magical structure with a central energy core
  Then the spell determines things like:
  * the color of the energy
  * the shape of the central rune
  * the geometry of the crystal/energy
  * the symbols orbiting the tower
  * the behavior of the rune circle
  * the particles emanating from it

  So a fire spell might have angular, rapidly rotating fragments and a turbulent core, while an ice spell has crystalline structures and slow orbiting runes.

## 6. Battlefield Shaping / Crowd Control

* **Ice wall (decided):** a destructible blockade — physically blocks a lane, and enemies that reach it attack it directly (it has HP) rather than routing around. Not a *persistent* blockade though: it also expires passively after a duration cap if never broken, so it can't wall off a lane forever if nothing engages it. Either way (broken by enemies or expired), a regrow cooldown starts, after which the wall reforms.
* A rune that makes the wall explode on break/trigger is planned.

## 7. Towers: Damage & Repair

* Common case when a tower takes damage: disabled, not destroyed. The active fighting character repairs it by funneling mana into it.
* Rare case (true destruction): attached runes return to the player's inventory, never lost.
* The Sapper enemy archetype is the one that meaningfully threatens towers — a visible, prioritizable threat, not universal collateral risk.
* Disabled towers show on the minimap.
* **Repair/Destroy interaction (decided):** both reuse the same reticle + raycast targeting as tower placement (Section 5), capped to roughly the same interaction range — not usable from across the map. When a tower is in view, a contextual world-space prompt appears near it ("Repair" / "Destroy"). Repair is a single press — frequent and low-stakes, matching its role as the common case above. Destroy is hold-to-confirm (~1s) with a progress indicator on that same prompt, rather than a separate confirmation dialog, so it doesn't break gameplay flow — cancels if released early or if the raycast loses the tower. Chosen over a Dungeon-Defenders-style persistent "mode" toggle specifically to avoid mode-confusion risk on the harder-to-reverse action.

## 8. Economy

* Two currencies: match-only **mana** (spent on towers/tokens, accrues passively over time, also spends to skip the death-respawn wait) and persistent **gold** (earned per mission, spent on meta-progression and at a spell-table crafting station — put an item in, randomly add/remove a mod).
* Income tower: fires a "spirit" that an enemy absorbs; the player must personally kill that enemy in time to cash in bonus income (the carrier is immune to tower damage). Self-limiting via player attention. **One spirit in flight at a time.**
* Co-op: capacity and currency both shared during a match; leftover currency splits evenly at the end.

## 9. Enemy Design

Philosophy: trade-offs, not gates. Soft pressure (tanky/slow vs. fast/fragile, grouping behavior, timed bursts, partial resistances) over hard immunities. No elemental resistances on enemies — elemental typing is a player-facing build axis only.

Roster (initial sketch): Fodder, Ranged Attacker, Tank, Flyer, Sapper (threatens towers), Assassin-type.

Difficulty tiers differentiate via composition and timing, not flat stat multipliers — avoids the "bullet-sponge" problem of higher difficulty just feeling slower.

* **Leash range (decided):** if the player character comes within a small leash range of an enemy, it breaks off its lane advance to chase and attack the player instead. If the player gets far enough away, the enemy gives up and returns to its lane route. Same "break from default movement, act, resume" shape as the ice wall (Section 6) — worth one shared behavior pattern rather than bespoke logic per case. Movement-architecture implication: chasing/returning covers arbitrary positions off the lane, which is the one case that still needs real pathfinding even if lane-following itself moves to fixed waypoints — see Section 15.
* **Enemy behavioral traits — architecture principle for later, not yet needed:** when a future enemy (Flyer, Ranged Attacker, etc.) needs genuinely different *behavior*, not just different stats, and that behavior could combine independently with another enemy's behavior — a flying ranged enemy being both at once — give `Enemy` a swappable behavior object for it (e.g. an `IMovementBehavior`, an `IAttackBehavior`) rather than a subclass. Subclassing works fine for one specialization at a time, but breaks down the same way `SpellCastContext`'s old class hierarchy did the moment two independent traits need to combine on one instance (Section 13). Not a new pattern to invent — `ProjectileHitEffect` and `SpellCastContext`'s `Projectile`/`Chain`/`Area` components already do exactly this elsewhere in the codebase. Considered and rejected: adopting full ECS (entities as bare IDs, components in packed arrays, all behavior in separate systems) for the project as a whole — the composability benefit only applies to the handful of spots where independent traits actually combine, not everything, and the performance benefit is built for cache-friendly batch processing across thousands-plus entities, well past what this game's hundreds of enemies need. Nothing to do yet — `Enemy` has no behavioral subclassing at all today — this is guidance for when Flying/Ranged actually get built, not a task for now.

## 10. Itemization & Equipment

* Character equipment: 6 slots (Weapon, Helmet, Chest, Legs, Boots, Gloves), each holding an Item with tiered Modifiers (T1 strongest/rarest → T5 weakest/commonest, gated by item rarity Mythic→Common).
* The Architect and fighting characters have **separate** equipment/mod pools.
* Item mods are a fully separate system from Runes (no shared class/slot mechanics) — but reuse the same `Apply(context)` shape internally, so the same infrastructure covers both.
* Damage resolves as `Base * (1 + IncreasedPercent) * MoreMultiplier` (PoE-shaped) specifically so equipment mods have a clean bucket to plug into later without another pipeline rework.
* Avoid flat "+X% damage" as the *only* kind of mod — items should let players "break the rules" (e.g. a unique that collapses a spell's projectiles into one, damage summed), not just tweak numbers.
* Not yet designed: mod pool contents, weighting, drop sourcing.

## 11. Multiplayer (Co-op)

* Hard requirement, invite-a-friend only (no public matchmaking). Built after single-player but architected for from day one — see Section 14 for the concrete implications.
* Prep phase: both players act as independent architects simultaneously, sharing one capacity/currency pool.
* Pause allowed in single-player only.

## 12. Development Notes

* The Rune/Tag/Spell composition system was spike-tested before anything else was built, since it was the personal go/no-go condition for the project — passed (composes cleanly, proven in a working test scene). Production is underway.
* Content (skills, runes, enemies, items) is data-driven via Godot `Resource` assets, not hardcoded, so content iteration doesn't slow down as the roster grows.

## 13. Class/Object Architecture

**Cast pipeline, at a glance:**

1. **`Spell`** (e.g. `FireballSpell`) — the immutable definition. Base stats and tags for one skill. Lives once, shared by every tower using it.
2. **`SpellInstance`** — one per placed tower. Wraps a reference to a shared `Spell` plus that tower's own attached `Rune` list and cast/cooldown state. This is "the tower's loadout," not a projectile.
3. **`SpellInstance.Resolve()`** — on cast, applies every attached `Rune` on top of the `Spell`'s base values and produces a **`SpellCastContext`** — a plain data snapshot of the final resolved stats for this one cast. Transient; discarded after the cast reads it. `SpellCastContext` is a single concrete class (no subclass hierarchy) carrying universal fields (`Range`, `Damage` as a `DamagePacket`, etc.) plus a set of *optional* component objects — `Projectile`, `Chain`, `Area`, `InstantHit` — each null unless the spell (or a rune) actually needs it. A `Spell`'s own `CreateBaseContext()` decides which components it starts with; a rune can also lazily create one it didn't start with (e.g. `ChainRune` can grant chaining to a spell with no `Chain` component at all).
4. **`CastEffect.Cast(context, spawnPoint)`** — each `CastEffect` (`ProjectileCastEffect`, `InstantHitCastEffect`) declares `CanHandle(context)`, checking for its own relevant component (`context.Projectile != null`, `context.InstantHit != null`). `Ritual` auto-discovers whichever `CastEffect` children it has and picks whichever one says yes — adding a third delivery mechanism later (a Beam, say) means adding one new `CastEffect` node under `Ritual` in the editor, no changes to `Ritual.cs` itself.
5. **`Projectile`** — the actual flying object. Fully independent once spawned: its own damage, radius, pierce count, hit-tracking. Doesn't reference the `SpellInstance` or its siblings.
6. **`ProjectileHitEffect`** (e.g. `ExplodeOnHitEffect`) — reacts when a `Projectile` hits something. Also the right extension point for future on-hit behavior (e.g. splitting into new projectiles), since each `Projectile` already carries its own independent state by this point.

`Spell` → `SpellInstance` (per tower) → resolve into a `Context` (per cast) → `CastEffect` spawns `Projectile`s (per world object) → `HitEffect` reacts (per hit). Each arrow is a hand-off to something new and independent — nothing downstream reaches back upstream.

**Why `SpellCastContext` is one class with optional components, not a subclass tree (decided):** the original design had `ProjectileCastContext`/`InstantHitCastContext` inherit from a shared `ChainableSpellCastContext`, with AoE fields pushed onto whichever base needed them. That broke down once a spell needed two capabilities at once with no natural is-a relationship between them — `FireballSpell` is both a `Projectile` *and* `AoE`, but neither specializes the other, and C# only allows one class-inheritance path. Patching it with more subclasses (`AoeProjectileCastContext`, etc.) trades one problem for a worse one: a new concrete class for every *combination* of capabilities that gets used, which also silently assumes every spell sharing a base wants every capability that base carries (not true — a hypothetical single-target Ice Spear projectile has no use for `Area` at all). The fix: capabilities that are independently combinable (matching how `Tag`s already work) live as nullable component objects on one flat context, checked with `!= null` rather than encoded in the type hierarchy — the same idea ECS-style architectures use for entity components, borrowed narrowly for this one class rather than adopted as the project's overall architecture. Whether a fuller ECS approach is worth adopting more broadly (e.g. for `Enemy` variants) is a separate, deliberately deferred conversation — not decided.

**Class notes:**

* **Spell** — the immutable definition (Resource). Since many towers reference the same Spell asset in memory, no mutable state (like attached runes) lives on Spell itself — that's what SpellInstance is for. A spell's baseline `Damage` is a `DamagePacket` (one float per element — Physical/Fire/Water/Cold/Lightning/Wind), assembled from six per-element `[Export]` floats (`BaseFireDamage`, etc.) declared on `Spell` — a future multi-element spell just sets more than one of them, no special-casing needed. Rule for where a stat's base value lives: universal stats (Range, Cooldown, Damage, RagdollForce) are flat fields on `SpellCastContext` itself; capability-specific stats (ProjectileCount, ChainCount, AreaMultiplier) live on the relevant optional component (`ProjectileCastData`, `ChainCastData`, `AreaCastData`), which a Spell's `CreateBaseContext()` only populates if that spell actually has the capability.
* **CastEffect family** — `ProjectileCastEffect`/`InstantHitCastEffect` today; more (`ZoneEffect`, `BeamEffect`) can be added later purely as new `CastEffect` subclasses with their own `CanHandle` check — no changes needed to `Ritual` or any existing effect.
* **Rune** — its own class: tier, required/granted tags, the data transformation it applies, any event hooks it registers.
* **TriggerBinding** — pairs a trigger condition (on-activate, on-break, on-hit) with a Spell to cast in response, making trigger-chaining inspectable data instead of hardcoded per-effect logic.
* **Ailment** — temporary state living on an Enemy (elemental tags for swirl reactions, CC immobilize, income-spirit-carrier flag). An Enemy holds a list of these rather than special-casing each into the Enemy class.
* **Tower** — HAS-A SpellInstance (composition, not inheritance). Tower owns position, capacity cost, HP/disabled state; SpellInstance owns the attached runes. Keeps "runes return to inventory on destruction" clean, and lets the Spell definition be shared safely across many towers.
* **PlayableCharacter** — thin shared base (position, input); fighting characters get a `CombatComponent`, the Architect gets a `BuildComponent` — composition over a deep inheritance chain.
* **Enemy** — mostly one generic, data-driven class (stats from a data asset) rather than a subclass per type, since most of the roster differs only by stats/flags. Reserve real subclassing for enemies with genuinely unique logic (Sapper, income-spirit carrier).
* **DefendableObjective** — generic name for the shell/harvester loss-condition object, so flavor can change without renaming code. Both the main shell and Energy Harvesters (Section 2) are this same type.
* **Item** — one equippable-to-character class covering both the Architect's own meta-progression buffs (Section 3) and fighting-character tower-behavior-changing uniques, rather than two parallel systems. Holds a list of **Modifier**s (one class with a `SlotType` enum — Prefix/Suffix/Unique — rather than three subclasses, since prefix/suffix are behaviorally identical at runtime). Item mods deliberately don't inherit Rune's constraints (e.g. Rune's one-per-type rejection is wrong for stackable itemization).
* **WaveDefinition, MapDefinition, Lane, EconomyManager** — sensible as initially sketched, no changes.

## 14. Multiplayer Architecture Implications

* **EconomyManager must be host-authoritative from day one.** Both mages spend from one shared pool simultaneously (Section 11); if clients each mutated a local copy, simultaneous spends would desync. Pattern: one source of truth on the host; a client's spend is a request, the host validates and broadcasts the confirmed result.
* Every state-changing action needs the same request/validate/broadcast pattern — placing a Tower, attaching a Rune, casting a Spell, triggering a token, repairing a tower. Build this in from each system's first implementation rather than retrofitting later.
* Enemy simulation is host-authoritative and single-sourced — clients receive state and interpolate, rather than each running their own simulation (which would drift out of sync from timing/floating-point differences).
* Spell/Rune data syncs as small IDs referencing a static data table, not fully serialized objects — both clients already have the transformation logic locally.
* Player death/revive needs its own explicit synced state (respawn timer, "being revived" status).
* Godot 4's high-level multiplayer API (`@rpc` annotations, multiplayer authority settings) covers these patterns directly — this is applying existing engine tools to the classes above, not building plumbing from scratch.

## 15. Open Questions

* Sniper vs. Assassin differentiation — both will ship, exact difference not yet designed.
* Full scope of the elemental tag system — more elements beyond Fire/Water/Cold/Lightning/Wind, and how conversion runes work.
* Damage roll ranges (PoE-style min/max per hit) vs. flat deterministic damage — undecided. Current multiplicative stacking (chain falloff, remaining-chain bonus, rune "more" multipliers) already makes exact breakpoints hard to hand-calculate, which weakens the "ranges hurt planning" argument against them.
* Critical hit system — not yet designed; floated alongside the roll-range question above, since crits and damage ranges tend to pair naturally.
* **Mana/capacity cost rounding — tentative, not fully settled.** `SpellCastContext.ManaCost`/`CapacityCost` stay float all the way through rune resolution (`base * (1 + increased%) * more`, same shape as Damage/Range); `EconomyManager` only converts to `int` at the very last step, and currently rounds up (`Mathf.CeilToInt`) rather than to nearest, so a resolved cost like `10.2` always costs `11`, never rounds down to a free fraction. Ceiling felt like the safer default (never undercharges), but it's not fully committed to — revisit if it starts feeling punishing once real per-rune multipliers exist instead of the current flat testing value (Section 5).
* **Elemental reactions — design philosophy and combination map (in progress):**
  * **Departs from Genshin's automatic-pairwise model.** Towers auto-fire constantly in a TD, so any reaction that triggers automatically whenever two elements touch the same enemy becomes ambient background noise rather than a deliberate moment — this is why Overload-style AoE knockback was ruled out. Reactions instead require a **dedicated consumer** (a specific rune/tower built to trigger off an existing element tag) — incidental crossfire between two "vanilla" elemental towers does nothing beyond overwriting the tag.
  * **Vocabulary (decided):** three separate concepts, kept deliberately distinct so they don't blur together in design discussion —
    * **Status** — single-slot, whichever element most recently hit the enemy (renamed from the earlier "element tag," then "Aura"). Purely a marker for "is there something here a dedicated consumer could trigger off of." Gets overwritten by the next elemental hit regardless of whether anything consumed it.
    * **Ailment** — a named, duration-based effect (e.g. Burn: damage over 3s, or a Lightning-Rod-style debuff) applied *to* an enemy, living in a list on the Enemy (renamed from the earlier "status effect," then "Effect" — freed up once the element marker above moved off "Aura" and claimed "Status" instead), per Section 13's existing note — multiple can stack/coexist independently, since they don't need to react with each other the way a Status does.
    * **Reaction** — what happens when an incoming hit's element touches an enemy's *existing* Status. Always opt-in: only triggers because a specific rune on the *attacking* spell checks for it (never automatic — see below). A reaction rune reads the target's current Status before this hit overwrites it, and if it matches what that rune reacts off of, does whatever bespoke thing the reaction does (e.g. **Overload** would be a rune that makes Lightning damage react with a Fire Status). The Status itself stays enemy-owned state; the decision to check it and act on it belongs to the rune.
  * **Ruled out:** automatic knockback/CC bursts on incidental double-hits (too disruptive and too frequent given automated tower fire). Actual elemental *resistance* (an element dealing reduced damage to a Status) was also considered and rejected — it has the same automatic/incidental-punishment problem, since a passive rule fires on every qualifying hit, not just deliberate ones.
  * Not every element needs to be symmetric — Wind is consumer-only (a Swirl-style effect triggered by a Wind attack landing on any enemy with a Status) and never itself becomes a Status other elements can consume, matching how Anemo works in Genshin. **Swirl is baked directly into any Wind-dealing spell, not implemented as a separate reaction Rune (decided)** — the one deliberate exception to "each reaction is its own Rune" below. Justified because Wind has no independent identity outside the reaction system to begin with (unlike Fire/Lightning, which have their own base-damage identity separate from whatever they react with) — a Wind-dealing spell's entire purpose already *is* Swirl, so gating it behind a separate rune would just add a layer over a distinction that doesn't actually exist. This doesn't reopen the "no automatic reactions" concern either, since that rule specifically targets disruptive/CC spam (Overload-style) firing every attack cycle — Swirl's effect (bonus damage + spreading/refreshing the tag) isn't in that category, it's closer to the already-established "pure damage-multiplier reactions don't need a cooldown" bucket below.
  * **Implementation plan (decided): each reaction is its own Rune, not a hub toggle or a passive/automatic system** — except Wind/Swirl (see above), the one deliberate exception, baked into the spell itself rather than gated behind a rune. Reuses the existing rune-socketing infrastructure entirely rather than inventing a parallel customization layer — a reaction rune is gated behind `RequiredTags` like any other, and costs a socket like any other, so picking a reaction variant is a real build tradeoff (opportunity cost against other runes), not a free settings-menu preference. This also means a single pairing can have *multiple* competing rune options once designed (e.g. a "Blister Rune" vs. a "Scalding Rune" for Fire-consumes-Water) — they just compete for the same slot, so adding a new variant later never requires touching the underlying architecture, only authoring one more `.tres`.
  * A reaction rune with a disruptive/CC component (knockback, stun) should carry its own internal per-enemy cooldown (e.g. ~5s) so the *same* lingering enemy can't be re-triggered every attack cycle — this is what makes something like an Overload-style rune viable at all despite being risky in the automatic model. Pure damage-multiplier reactions (Melt/Vaporize-style) don't need this, since there's no chaos risk in them re-triggering often.
  * **Goal, not yet started:** at least one working reaction option for every pairing in the map below, even if simple — the map exists to track that coverage as each is designed.
  * **Combination map** — what a dedicated consumer of the row element does on an enemy currently carrying the column element as its Status. Fill in as each is decided.

  * **Per-element damage (decided, implemented): `DamagePacket`.** Originally scoped as a single `ElementTag` field riding alongside a flat `Damage` float, but that breaks the moment a Reaction/Ailment needs to know *how much* of a hit was a given element (e.g. a Lightning-Rod-style Ailment redirecting a percentage specifically of the Lightning portion of a hit) — a tag next to one number can't express that. Final shape: `DamagePacket` (`PhysicalDamage`/`FireDamage`/`WaterDamage`/`ColdDamage`/`LightningDamage`/`WindDamage`) replaced the flat `float Damage` throughout the cast/hit pipeline (`Spell.BaseDamage`, `SpellCastContext.Damage`, `Projectile.Damage`, `ChainResolver`, `Enemy.TakeDamage`), surviving all the way to `Enemy.TakeDamage` intact. `Enemy.Status` tracks `DamagePacket.DominantElement` (excluding Physical and Wind from candidacy, per Wind's consumer-only design above) on every elemental hit — the data a Reaction rune would read is in place, though no actual Reaction rune has been built yet. `SpellInstance`'s "increased/more" formula and both chain-falloff implementations needed no logic changes for this, only a type change, since `DamagePacket` defines its own scalar multiplication operator.
  * **Lightning Bolt rune brainstorm — generalizability audit.** Every rune should hook into a *tag*, not a specific spell class, so it automatically applies to any future spell sharing that tag (same principle that already makes Pierce/Chain/Return/Increased Area work across any eligible spell) — worth explicitly checking each new idea against this rather than assuming it's fine:
    * **Prime** — debuff "Primed" on an enemy; the next hit tagged `Tag.Lightning` (any spell, not just Lightning Bolt) landing on a Primed enemy sparks a random *nearby* enemy (not the nearest — no anchor/group tracking needed, evaluated fresh per hit off the struck enemy's own position). The per-element damage plumbing it needs (`DamagePacket`/the Status marker) now exists, so this is unblocked, but not yet built. Must be capped to trigger at most once per cast (mirrors why `ExplodeOnHitEffect` only fires on the terminal hit, not every chain jump) — without that cap it can compound with `ChainRune` worse than Fireball's Chain+Explode ceiling does, since Fireball's explosion is already bounded to one shot per cast and Prime currently isn't.
    * **Cast speed** — fully generalizable already, spell-agnostic. Works on anything, pays off best on spells with no travel delay (Lightning Bolt) since a faster Fireball still loses time to its projectile's travel.
    * **Fork (decided): gates on chainable spells, not `Tag.Projectile`.** Strikes multiple simultaneous initial targets, each starting its own chain — deliberately diverges from PoE's own Fork (a projectile-splitting mechanic) in favor of fitting this project's chain-centric spell shape instead.
    * **Projectile speed** — a real, currently-missing lever. `Projectile.speed` is hardcoded (`private float speed = 20f`), never threaded through `Initialize()`/the context — would need the same small plumbing treatment `Radius`/`AreaMultiplier` already got before a rune could touch it.
* **`ChainableSpell` usage (decided):** reserved for spells where chaining is inherent to the spell's identity (e.g. `LightningBoltSpell`), not for projectiles that merely *can* chain if a `ChainRune` is socketed. `FireballSpell` extends `Spell` directly and declares nothing about chaining — `ChainRune`'s tag gate (`Chaining` or `Projectile`) plus its own lazy `context.Chain ??= new ChainCastData()` are enough to make any projectile or instant-hit spell rune-chainable for free, granting the `Chain` component to a spell that doesn't start with one, matching how `PierceRune`/`ReturnRune` already work. To close the gap this used to paper over (`ChainRune` only ever set `ChainCount`, never `ChainRange`), `ChainRune` carries its own `FallbackChainRange` and applies it non-destructively via `Mathf.Max`, so a rune-granted chain always has reach without ever shrinking a spell's own inherent range.
* **`ExplosionRadius` placement (decided):** stays on `ExplodeOnHitEffect`, not threaded through `ProjectileCastData`/`Projectile` — those types describe things `Projectile` itself acts on (flight/collision behavior), whereas explosion behavior is entirely owned by the swappable `ProjectileHitEffect` strategy, which exists specifically so `Projectile` never needs to know about it. `fireball_spell.tres` embeds its own `ExplodeOnHitEffect` as a local sub-resource (not an external shared `.tres`) so the radius is still authored right there when you open Fireball's own resource, without any runtime duplication/override code — the embedded copy simply isn't shared with any other spell, so nothing can stomp it. `Projectile.Radius` (the projectile's own physical size, separate from blast radius) is unrelated and does get threaded through the context (via `context.Projectile.Radius`), since that one *is* core `Projectile` behavior (it now scales the projectile's own mesh/collision shape at spawn). That scaling (`BodyMesh.Scale = Vector3.One * Radius`, a uniform scale on all axes) assumes a roughly round mesh — flagged, not yet a problem: a future non-round projectile (e.g. an elongated Ice Spear) would need its own scaling formula for that one line, not a change to where `Radius` lives.
* **`ChainDamageModifier` placement (decided):** `MoreDamagePerRemainingChain` no longer lives as a raw float on `ChainCastData`/`ChainableSpell` — it's `ChainDamageModifier`, an optional swappable `Resource` hook (`GetMultiplier(int remainingChains)`), following the exact shape `ProjectileHitEffect` already established for `ExplosionRadius`. Same reasoning: `ChainCastData` is shared by every chaining spell (`Projectile`'s own chain-redirect path reads it too), so a raw field there implicitly meant "any spell could use this," even though it only ever described Lightning Bolt's own finisher-damage curve. `LightningBoltSpell` embeds its own `FrontLoadedChainDamageModifier` sub-resource (same embedding pattern as Fireball's `ExplodeOnHitEffect`); `Projectile`/`ChainResolver`/`FireballSpell` never reference the concept at all, only the nullable hook.
* Equipment mod pool: contents, weighting, drop sourcing.
* **XP / meta-progression scope for the vertical slice (decided): full persistent XP + item-drop progression** (Section 3) — not deferred to session-only gold.
* Specific low-poly art style/visual identity — not urgent yet, will matter for silhouette readability once designs are more concrete.
* Wave-end safety net: a wave should auto-end after a timeout even if enemies remain (e.g. one stuck on the navmesh) — not implemented yet.
* Non-lethal knockback: `KnockbackForce` currently only applies via the on-death ragdoll launch. A hit that knocks back *without* killing needs a different mechanism (a living enemy is `CharacterBody3D`-driven, not free ragdoll physics) — not designed yet.
* Ritual line of sight and non-horizontal projectile aiming: both confirmed as needed eventually (Section 5), neither implemented yet.
* **Enemy movement architecture (planned, not yet built) — hybrid shared-lane waypoints + one-off pathfinding for displaced enemies.** Currently every enemy runs its own full `NavigationAgent3D`/navmesh query every physics frame for its entire route, even though most enemies on a lane are walking the identical path — wasteful given waves run 50-70 enemies. Planned replacement, in build order (ice wall, below, is the intended first real test case — an obstacle that forces enemies off their lane and back on):
  1. **Lane waypoint system** — a `Lane` class per spawner computes its path once (a single static navmesh query, not a live per-enemy agent) and exposes it as an ordered waypoint list; enemies walk toward the next shared waypoint and advance their own index, instead of querying the navmesh themselves.
  2. **Player health** — `MaxHealth`/`TakeDamage` on `PlayerCharacter` (mirrors `Enemy.TakeDamage`'s shape), needed before enemies can meaningfully attack the player. Damage-taking only for this pass — respawn/revive (Section 4) is separate, larger scope.
  3. **Leash detection, chase, and attack** — an enemy checks distance to the player on an interval (mirrors `Ritual.TargetSearchInterval`, not a per-frame check); inside leash range it breaks off lane-following for a one-off real pathfind toward the player; inside attack range it deals damage on a cooldown (a sustained melee loop, deliberately different from `DefendableObjective`'s current contact-instakill placeholder — that gets reworked to match once enemies can actually attack).
  4. **Give-up-and-rejoin, across lanes (decided):** once the player is far enough away, one more real pathfind query to the nearest waypoint across *every* lane, not just the one the enemy started on — an enemy that wandered off its lane can rejoin a different lane if that's what ends up closer, not forced back to its origin.
* **Rune/spell iconography — undecided between two directions:**
  * *Procedural sigil generation:* 30 anchor points evenly spaced on a circle (26 letters + 4, one per rune slot). A spell or rune's name maps its letters to points and connects them in sequence, generating a unique glyph without hand-drawing one per rune. When a rune is socketed, its glyph is anchored through its slot's dedicated marker point and overlaid on the spell's own glyph — so a fully-built tower's sigil is a compound of the spell's glyph plus each attached rune's glyph layered together (chosen over an alternative where each rune reroutes a single shared path, since overlay is order-independent and each rune's glyph is cacheable on its own). Socketing a rune would animate in — a stroke-reveal "growing outward" effect via `Line2D` + `Tween`, segments staggered slightly rather than growing in lockstep, easing into place at the anchor point.
  * *Functional iconography:* instead of (or blended with) letter-based glyphs, hand-draw a small fixed set of primitive strokes tied to mechanical tags/categories (a projectile-pattern primitive, an AoE-radius primitive, a duration/DoT primitive, etc.) and procedurally compose those per rune based on which tags it touches — same overlay/animation system, but the player can learn to read a tower's build at a glance instead of memorizing arbitrary shapes. Trades some of the procedural version's novelty for legibility, without reintroducing a "hand-drawn icon per rune" art bottleneck that would work against Section 12's data-driven/scalable-content principle (primitives are reused across every rune sharing a tag, not authored per rune).
  * Not needed for the vertical slice — revisit once core gameplay is playable.
  * **Prototyping notes (in progress, both untested as of writing):**
    * *Letter-based prototype* (`ui/sigils/SigilPreview.tscn` + `SigilGenerator.cs`): 26 anchor points on a circle, one per letter, a name's unique letters (duplicates skipped) connected in sequence, with an angled flare drawn at the two open ends of the path. Tried and found lacking — words with many repeated letters still look cluttered even with dedup, and short/low-variety words often don't self-intersect at all, reading as a plain polygon rather than a woven sigil. Root cause: the technique this was based on (chaos-magic word sigils) was never really "type a word, get finished art" even historically — practitioners always hand-restyled the plotted skeleton afterward, so raw procedural output was probably never going to look finished on its own.
    * *Tag-based prototype* (`ui/sigils/TagSigilPreview.tscn` + `TagSigilGenerator.cs`/`TagAnchorDisplay.cs`/`TagSigilCandidatePanel.cs`): the follow-up idea — anchor points represent `Tag` enum values (currently 10: Projectile/AoE/Duration/Trigger/Chaining/Fire/Water/Cold/Lightning/Wind) instead of letters, so point count is designer-controlled rather than dictated by English spelling, and spells sharing tags naturally share partial glyph structure (closer to the "functional iconography" alternative above, but via the same connect-the-dots mechanism rather than hand-drawn primitives). A future extension, not yet built: also deriving points from behavioral keywords (e.g. a spell "travels horizontally" vs. "flies") to distinguish same-tag spells further — shelved for now due to needing its own small vocabulary/taxonomy design. UI toggles each tag on/off, shows the full anchor circle with active tags highlighted, and renders 4 candidate glyphs side by side (Angular / Star / ActivationOrder / SeededShuffle orderings of the same active point set) so a shape can be picked by eye rather than computed. **Coded but not yet run or visually evaluated** — next step when picked back up.
    * Anchor-point-count tradeoff (applies to either direction): square numbers have no special significance for points evenly spaced on a circle (that instinct carries over from grid layouts, not circular ones). What actually matters: total vocabulary size should come from counting up what's actually needed, not picked as a round number first; more points means anchors sit closer together angularly, which past some point (rough guess, unverified — maybe 10–16) makes near-neighbor connections start looking like noise instead of a deliberate stroke. Total vocabulary size and per-glyph clutter are different knobs — a bigger vocabulary means more possible distinct shapes across the whole roster, not a busier individual glyph, since that's driven by how many tags one spell actually has. Adding a new tag/point later reflows every existing glyph's angles (angle = 360°/N) — a non-issue pre-ship, but worth reserving a few unused slots before locking the vocabulary at ship time so existing runes' icons don't shift once players have learned to recognize them.
* **Rune naming — thematic goal, pass complete:** every rune's display `Name` is now a single evocative word instead of a literal mechanical description, the way a lot of ARPGs name their modifiers — **Haste** (cast speed), **Fork**, **Extend** (range), **Velocity** (projectile speed), **Salvo** (multi-projectile), **Expand** (increased area), plus **Chain**, **Pierce**, **Nova**, and **Return**, whose existing names already fit and didn't need changing.
* Navmesh re-baking on tower placement (surfaced while planning tower placement): placed Rituals now have solid collision, but `NavigationBaker.cs` only bakes once at level load — enemies won't route around anything placed afterward. Idea, not yet built: re-bake once at the end of a build phase, and once whenever a reactive token is used mid-wave, rather than baking on every individual placement (expensive) or never (broken pathing).
* **Time-travel theme, still open:** where the hub sits — outside time entirely, or anchored in one fixed era — not yet decided between the two. Per-era content scope (how many eras for a real release, how much distinct roster/biome per era, whether some assets are shared across eras or every era is fully bespoke) is entirely TBD; not a vertical-slice concern. Boss-tier enemies (the "weakened prison bonds" premise) aren't in the Section 9 roster sketch yet — the theme motivates adding a boss archetype, but design (how a boss fight works mechanically in a lane-based TD) isn't started.

7. ~~Wave-end handling~~ — `WaveController` waits for the `"enemies"` group to empty before flipping back to Build phase. A stuck-enemy safety-net timeout is still open (Section 15). **done.**
8. ~~Win/lose state~~ — `GameOverHandler` reloads the scene on `EventBus.GameEnded` (objective destroyed = loss, all waves cleared = win). Still just a console print + reload, no UI polish — fine for a slice. **done.**

Vertical slice was called feature-complete above prematurely — the loop it covers (place towers, survive a wave, win/lose) works end to end, but a real vertical slice needs to touch every system central to the game's identity (Section 1), not just the core combat loop. Also needed before the slice is real:

9. ~~Gold~~ — the persistent second currency (Section 8) is real: a `Gold` field on `PlayerSaveData`, `EconomyManager.GoldEarned` accumulates 1 per enemy kill (`Enemy.GoldReward`, tunable per enemy type) during the match, and `GameOverHandler` folds that plus a flat victory bonus into `Data.Gold` and saves on a win. The crafting station to actually *spend* it doesn't exist yet — rolled into the Items/equipment step below rather than tracked separately. **done.**
10. **Ice Wall tower** (Section 6) — next up. Implemented as a real `Spell` (`IceWallSpell`) like any other, not a bespoke system, so it goes through the existing placement/economy/rune pipeline. Design still being finalized as of this note: two-stage placement (wall location, then a linked tower — destroying the tower breaks the wall too), a `Range`-gated placement distance plus a separate enemy-proximity-to-the-wall detection radius that decides when the tower actually spends its cooldown, and a segmented wall (minimum 2, more for a longer run, each segment its own health pool) so a lane can't be fully blocked by a token-sized wall. A general-purpose `CastTrigger` hook (a `Resource`, mirroring `ExplosionRadius`/`ChainDamageModifier`'s swappable-hook pattern) is planned for the "wait until an enemy is near" gating, deliberately kept spell-agnostic so a future "if an enemy steps here" trigger-rune can reuse it rather than needing its own mechanism.
11. **Enemy movement architecture** (Section 15) — right after Ice Wall specifically because the wall is the first real obstacle that forces enemies off a straight lane path, making it the natural test case for the planned shared-lane-waypoints + one-off-pathfind-when-displaced rework, rather than validating it in the abstract.
12. **Items/equipment** — zero implementation (Section 10). Needs at minimum the `Item`/`Modifier` classes, equipment slots on a character, mods actually affecting gameplay, and the spell-table crafting station (put an item in, randomly add/remove a mod) that gives Gold something to spend on.
13. **At least one or two working Elemental Reactions** — the Status/`DamagePacket` foundation exists (Section 15), but no actual Reaction rune has been built yet. Proving the concept end-to-end (e.g. Ember Spread, or Swirl) is enough for the slice; the full combination map can stay a post-slice goal.
14. **Tokens** — pre-crafted, reactively-deployed mid-wave towers (Section 2 & 17). Right now the wave phase has no reactive-building option at all, which undersells a mechanic the design treats as core to why towers-can't-reposition doesn't feel restrictive.
15. **Tower disable/repair loop** — `Ritual.Repair()` is currently a stub (`GD.Print` only), and nothing yet lets enemies damage a tower in the first place (Section 7). "Disabled, not destroyed, repaired by funneling mana" is the defining tower-damage identity, not yet real.

Smaller, lower-priority gaps noted for completeness, not blocking: Effects/status system (Burn, etc. — companion to Reactions), line-of-sight raycasting (already an open item in Section 15). Explicitly **not** required for the slice, per existing decisions elsewhere in this doc: additional fighting characters beyond Soldier (Section 4), co-op (Section 11), win/lose UI polish (already noted as fine above).

## 17. UI: Tower Construction & Deployment

`Q` drives two distinct flows that behave nothing alike — designed as two separate systems rather than one flexible menu, since they sit under opposite time pressure (prep vs. wave phase, Section 2).

* **Architect, prep phase — construction menu (decided):** `Q` opens a full-screen overlay: tag-filterable grid of available spells → select one → rune socket screen (4 sockets, one per corner, for now) → confirm → placement (reticle + raycast, Section 5). No time pressure, so this can be a rich browsing experience.
  * Socket state persists across backing out and returning to the socket screen for the same spell (an accidental cancel shouldn't lose 3 already-placed runes) — sockets only clear if the underlying spell selection itself changes.
  * A rune already socketed elsewhere on the same spell shows greyed out, sorted to the back of the list, with a short message explaining why — makes the existing one-per-type rule (Section 5) visible instead of silently rejecting the drop.
  * A per-rune "unsocket" action, plus a separate "clear all runes" bind gated behind a confirmation prompt (guards against wiping a near-finished build by accident).
  * Short rune description text (label + one-line effect, e.g. "+8 Proj — projectiles fire in a circle") lives as data on the `Rune` resource itself, not hardcoded per-rune in UI code.
  * Renders as a blocking overlay over the opening player's view. Since Section 11 has both co-op players able to build simultaneously, a true whole-game pause won't work — overlay likely needs to be scoped per-player (split-screen or similar); exact mechanism still open.
* **Any player, mid-wave — token deployment (decided):** `Q` opens an instant radial/hotbar pick among the player's up to 3 pre-crafted tokens (Section 2) — no browsing, no rune sockets, since a token's loadout was already locked in during prep. Optimized for speed under pressure, not depth.
* **Favorites/loadouts vs. tokens — distinct concepts:** a favorite is a saved spell+rune preset that speeds up normal construction (skip re-picking a common combination). A token is the separate, already-decided reactive mid-wave deployable. Same underlying data shape (spell + rune set), different purpose and moment of use — keep the vocabulary distinct so the two don't get conflated in implementation.
* **Navigation (decided):** built gamepad-first, not mouse-first-then-retrofit — discrete grid focus navigation (Godot's `Control`/`GridContainer` focus-neighbor system) rather than hover-based, with tag filters on their own input path (e.g. shoulder buttons cycling filters) so they don't collide with grid navigation.
